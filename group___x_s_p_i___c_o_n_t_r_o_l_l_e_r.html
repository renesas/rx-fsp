Detailed Description

Driver for the XSPI_CONTROLLER peripheral on RX MCUs. This module implements the SPI Flash Interface.

Overview

The XSPI_CONTROLLER peripheral supports xSPI compatible external memory devices, and it interfaces with these devices to perform data I/O Operations. The XSPI_CONTROLLER peripheral does not support addressable devices, so all connected memory devices must be connected to an individual chip-select pin. Please note that this document will reference the xSPI protocol to which XSPI is a subset. The XSPI_CONTROLLER peripheral is compatible with a variety of xSPI protocol operating modes.

Features

The XSPI_CONTROLLER driver has the following key features to support the xSPI device:

  • Perform data I/O Operation
  • Direct memory-mapped access to the xSPI device memory up to 256 MB.
  • Can be configured with xSPI devices on either of the 2 channels
  • Programming the xSPI device using combination write (up to 64 bytes)
  • Erasing the xSPI device
  • Sending device specific commands and reading back responses of up to 8 bytes
  • 1- and 2-byte addressing intended for row-column memories
  • 3 byte addressing
  • 4 byte addressing
  • Auto-calibration
  • Decryption-on-the-fly
  • Support for standard SPI frames, xSPI Protocol 1.0, xSPI Protocol 2.0, and xSPI Protocol 2.0 Extended frames.

Additional build-time features:

  • Optional (build-time) DMAC support for data transmission when used with XSPI_CONTROLLER.
  • Optional (build-time) XiP support for entering/exiting XiP mode of the target device.
  • Optional (build-time) Data-strobe (DS) auto-calibration support for target devices using the DS signal.
  • Optional (build-time) Decryption on the fly (DOTF)
  • Optional (build-time) Support for memory which use row-column addressing.
  • Optional (build-time) BSP initialization of SiP Flash.
Note
For XSPI_CONTROLLER, use of DMAC for data transmission is strongly recommended. Without the use of DMAC, due to the high-speed hardware design of the XSPI peripheral, data transmission can be sensitive to timing variance, which could cause software-based memory-mapped operations to fail unexpectedly.

Clock Configuration

The signals to the xSPI target device are derived from OCTACLK. OCTACLK must be set to twice the desired xSPI_CLK signal frequency. This allows data to be latched on either clock edge for Dual-Data-Rate modes (4S-4D-4D or 8D-8D-8D).

Please refer to the Hardware User Manual for the clocks which control the XSPI_CONTROLLER registers. These along with OCTACLK can be set on the Clocks tab of the RA Configuration editor.

Pin Configuration

The following pins are available to connect to an external XSPI device:

  • XSPIn_CK: clock output (XSPICLK / 2)
  • XSPIn_DS: data strobe signal
  • XSPIn_CS0: device 0 select
  • XSPIn_CS1: device 1 select
  • XSPIn_IO0: Data 0 I/O
  • XSPIn_IO1: Data 1 I/O

Usage Notes

Usage Notes for xSPI support

After R_XSPI_CONTROLLER_Open() completes successfully, the xSPI device contents are mapped to the appropriate external memory regions for each XSPI_CONTROLLER unit. For example, on the RX74M, R_XSPI_CONTROLLER0 maps the CS0 device to address 0x30000000 and the CS1 device to address 0x20000000. After opening, the addresses can be accessed like on-chip flash.

Bank CS0 and CS1 support up to 256 MB of address space each depending on the platform.

Auto-calibration

If support is enabled, auto-calibration procedures are triggered automatically when the 'Data latching delay' field in the configurator properties is set to 0. The user application is responsible for setting the appropriate preamble pattern before calling R_XSPI_CONTROLLER_Open() when using a data strobe (DS) mode or changing the SPI protocol to a DS mode using the R_XSPI_CONTROLLER_SpiProtocolSet() API. The appropriate preamble pattern can be written to the desired address using the R_XSPI_CONTROLLER_Write() API while in simple SPI mode (recommended), or a non-DS mode. Ensure that the same address is passed through the configurator. If the xSPI device is already in a DS mode, the preamble pattern must be programmed using the debugger before calling R_XSPI_CONTROLLER_Open().

The preamble pattern is expected to be { 0x00, 0x00, 0xFF, 0xFF, 0x00, 0xFF, 0x00, 0x08, 0xF7, 0x00, 0x00, 0xFF, 0xF7, 0x08, 0xF7, 0x00 }.

For high frequency operation (e.g. 266 MHz), it is recommended to enable the Output Assertion Delay to improve signal stability.

Chip Select Latencies

Chip select latencies can be set through the configurator. The default settings support SPI at minimum latency. In case the driver is opened in SPI mode and will be switched to DOPI mode later using R_XSPI_CONTROLLER_SpiProtocolSet(), please select latencies required for DOPI before calling R_XSPI_CONTROLLER_Open().

Usage Notes for OctaRAM support

Auto-calibration

If support is enabled, auto-calibration procedures are triggered automatically when the 'Data latching delay' field in the configurator properties is set to 0, the same as with OctaFlash.

Unlike OctaFlash, the user does not need to write a preamble pattern to the device before calling R_XSPI_CONTROLLER_Open() or R_XSPI_CONTROLLER_SpiProtocolSet(). For OctaRAM devices, calibration instead uses the target device's built-in Preamble Bit Data Pattern READ command (command code F0h, address 00h), which the OctaRAM drives unconditionally regardless of calibration or timing state. This avoids the chicken-and-egg problem of needing correctly calibrated timing to write the pattern in the first place.

Make sure to set up the option of OctaRAM via R_XSPI_CONTROLLER_DirectTransfer() after calling R_XSPI_CONTROLLER_Open() with 'Data latching delay' field in the configurator properties is other than 0.

Auto-calibration may also be triggered manually at any time by calling R_XSPI_CONTROLLER_AutoCalibrate() once the device is open.

Note
This behavior is specific to OctaRAM devices which support the Preamble Bit Data Pattern READ command (e.g. S66/S67WVO32M8DALL/BLL, see datasheet section 5.3). Confirm the connected OctaRAM part supports this command before relying on auto-calibration.

XiP Support

XSPI_CONTROLLER supports eXecute in Place (XiP) modes of operation. This can be used for read-only memory-mapped accesses to reduce overall read latency by skipping the command sequence in the xSPI transaction. Separate XiP enter and exit codes may be specified for either attached target device. Upon calling R_XSPI_CONTROLLER_XipEnter(), the associated memory region for the target device is switched to read-only mode and the enter code sent to the device. Calling R_XSPI_CONTROLLER_XipExit() will transmit the exit code and transition the memory region back to read-write access.

Only one flash device should be used after entering XiP mode. Once entered, XiP codes will be transmitted to all attached devices.

xSPI Commands

Command sets and erase commands may be specified individually for each supported protocol mode. By default, the configurator only supports an alternative command set for "High-Speed Mode" (DOPI 8D-8D-8D) mode. The command sets cannot be changed during run-time, but the appropriate command set will be selected when changing protocol modes. If a command set is not found, an FSP_ERR_INVALID_MODE error code will be returned.

If custom DOPI erase commands are not specified, ensure the erase commands are the appropriate 2-byte DOPI commands. The lower byte will be used for 1-byte command protocols.

If a custom command set table is provided, the primary erase command table must also be provided for backwards compatibility with some modules. The primary table contains the erase sizes being used during normal application runtime.

DOTF Support

Decryption-On-The-Fly is configurable for XSPI with OctaFlash and is disabled from the build by default. When DOTF support is enabled, each XSPI unit uses the matching DOTF unit:

  • DOTF0 is used with XSPI0.
  • DOTF1 is used with XSPI1.

DOTF decrypts data during memory-mapped reads from the configured XSPI address range. The encrypted data must be generated for the same physical address range that will be used by the application because the DOTF counter is address dependent.

  • DOTF0 operates within the address range 0x20000000 to 0x3FFFFFFF.
  • DOTF1 operates within the address range 0x40000000 to 0x5FFFFFFF.

Using the DOTF feature requires first creating the encrypted blob on the PC and then configuring the DOTF module with the same parameters so the programmed XSPI contents can be decrypted at run time. Use the Security Key Management Tool (https://www.renesas.com/us/en/software-tool/security-key-management-tool) to create the encrypted blob.

Example: To encrypt a 4096 byte area in an input srec file from 0x20000000 to 0x20000FFF using a 128-bit AES encryption key "FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF" and IV "00000000000000000000000000000000", use SKMT with the following arguments:

skmt.exe /encdotf /keytype "AES-128" /enckey "FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF" /nonce "00000000000000000000000000000000" /startaddr "20000000" /endaddr "20000FFF" /prg "input.srec" /incplain /output "encrypted_output.srec"

The values for key, iv and decryption area start and end addresses that were used to create the blob using SKMT must be set in the DOTF configuration in FSP.   • When the Compatibility Mode stack is added for the crypto engine, the user can provide either a wrapped or plaintext AES key to the DOTF module.
  • When the Protected Mode stack is used, only wrapped keys are supported.

When configuring the DOTF options, make sure that the key format is specified.

SiP Flash

SiP or System-in-Package devices, can contain an internally bonded XSPI flash memory in the package. The BSP supports startup initialization of SiP flash memories using the R_OSPI_B driver. To enable startup initialization, please select an appropriate stack under Storage > SiP Flash and enable the following properties in the BSP section of the configurator: OSPI > SiP Flash Support and RA Common > Early BSP Initialization. Both of these BSP properties must be enabled for successful SiP flash startup and initialization of other memory regions (e.g. RAM) which load data from the SiP flash.

Limitations

Developers should be aware of the following limitations when using the XSPI_CONTROLLER driver:

XSPI_CONTROLLER

  • The R_XSPI_CONTROLLER driver expects memory devices to have uniform sector sizes. If a design requires using a memory with non-uniform sectors, the end-user application must appropriately manage sectors.
  • Prefetch and combination support for memory-mapped access is applied globally to all slave devices per XSPI_CONTROLLER unit.
  • Combination writes are limited to a maximum of 64 bytes. The user should verify the write has completed before attempting to write more bytes.
  • Writing to the memory-mapped regions with the CPU is restricted to 64-bit accesses with 8-byte destination alignments. This restriction is not applicable to other bus masters (e.g. DTC or DMAC).
  • Take care to restrict concurrent accesses of the XSPI memory area. Collisions on the bus can occur if other bus masters attempt to write to the XSPI memory area while another master is reading the XSPI memory area.
  • When using 8D-8D-8D mode, care should be taken to access on even-aligned addresses. Problems may occur if odd address alignment is used. This restriction applies to all bus masters using XSPI_CONTROLLER.
  • DOTF: AES-192 is not supported when the Protected Mode stack is used.
  • When using the IAR compiler, XSPI data must be const qualified to be downloaded by the debugger.
  • Memories which use row-column addressing must be managed by the end-user application to ensure the appropriate memory row is loaded and stored.
  • When using SiP Flash with encrypted data, the encryption key and IV must be const qualified if BSP startup initialization is used. The SiP flash is initialized before the C-runtime has been initialized and before any RAM variables have been loaded from their respective non-volatile memories.
  • When using SiP Flash, secure partitions must be 32K aligned or programming and access may fail.

/*
* Example function to change from 1S-1S-1S (SPI) to 8D-8D-8D (DOPI) protocol mode.
*
* This assumes S28HS256 is in default factory configuration:
* - 3-byte address lengths
* - Memory read latency of 8/20 (1S/8S) up to 166 MHz DOPI
* - Register read latency of 0/3 up to 25 MHz DPOI
*
* @param [in] p_ctrl Pointer to the XSPI_CONTROLLER control struct.
*
* The OCTACLK source must be within range to support this example as written. Clocks are intended to be configured
* as follows to obtain a PLL2P frequency of 240 MHz and OCTACLK starting frequency of 60 MHz.
* HOCO (48 MHz) -> PLL2 -> /3 -> x60.0 {960 MHz} -> PLL2P /4 {240 MHz} -> OCTACLK -> /4 -> {60 MHz}.
*/
void r_xspi_controller_example_spi_to_dopi (xspi_controller_instance_ctrl_t * const p_ctrl)
{
fsp_err_t err = FSP_SUCCESS;
/* Step 1: Enable write access to the registers. */
xspi_controller_write_enable_and_verify(p_ctrl, false);
/* Step 2: Adjust the dummy cycles for a faster clock later.
* Changes the dummy cycles for register commands to 1 for SPI and 5 for OSPI.
*/
spi_flash_direct_transfer_t xfer_adjust_cfr3 =
{
.command = XSPI_CONTROLLER_COMMAND_WRITE_REGISTER_SPI_MODE,
.address = XSPI_CONTROLLER_DC_ADDRESS,
.data_u.data = XSPI_CONTROLLER_FAST_CLOCK_REGISTER_SETTING,
.command_length = 1U,
.address_length = 3U,
.data_length = 1U,
.dummy_cycles = 0U
};
err = R_XSPI_CONTROLLER_DirectTransfer(p_ctrl, &xfer_adjust_cfr3, SPI_FLASH_DIRECT_TRANSFER_DIR_WRITE);
assert(FSP_SUCCESS == err);
/* Step 3: Change the target flash's configuration to use 8D-8D-8D mode. */
spi_flash_direct_transfer_t xfer_change_mode =
{
.command = XSPI_CONTROLLER_COMMAND_WRITE_REGISTER_SPI_MODE,
.address = XSPI_CONTROLLER_MODE_ADDRESS,
.data_u.data = XSPI_CONTROLLER_DOPI_REGISTER_SETTING,
.command_length = 1U,
.address_length = 3U,
.data_length = 1U,
.dummy_cycles = 0U
};
err = R_XSPI_CONTROLLER_DirectTransfer(p_ctrl, &xfer_change_mode, SPI_FLASH_DIRECT_TRANSFER_DIR_WRITE);
assert(FSP_SUCCESS == err);
/* Step 4: Speed up the bus by lowering the input divider.
* If using the suggested clock settings this will increase the bus speed from 60 MHz to 120 MHz. */
xspi_controller_change_omclk(BSP_CLOCKS_OCTACLK_DIV_2);
/* Step 5: Transition the OSPI peripheral to DOPI mode. This will initiate auto calibration as MDTR is 0.
* This must happen after the device has been re-configured to the new mode. Otherwise, communications will be
* lost as both MCU and flash device will be in different modes. */
err = R_XSPI_CONTROLLER_SpiProtocolSet(p_ctrl, SPI_FLASH_PROTOCOL_DOPI);
assert(FSP_SUCCESS == err);
/* Step 6: Verify that the chip is in requested DOPI mode. */
spi_flash_direct_transfer_t xfer_read_register =
{
.command = XSPI_CONTROLLER_COMMAND_READ_REGISTER_SPI_MODE,
.address = XSPI_CONTROLLER_MODE_ADDRESS,
.data_u.data = 0,
.command_length = 1U,
.address_length = 4U,
.data_length = 1U,
.dummy_cycles = 5U,
};
err = R_XSPI_CONTROLLER_DirectTransfer(p_ctrl, &xfer_read_register, SPI_FLASH_DIRECT_TRANSFER_DIR_READ);
assert(FSP_SUCCESS == err);
if (XSPI_CONTROLLER_DOPI_REGISTER_SETTING != xfer_read_register.data_u.data)
{
__BKPT(0);
}
}
